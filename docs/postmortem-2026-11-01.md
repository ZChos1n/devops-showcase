# 故障复盘：showcase-api 5xx 错误率飙升

> 状态：已解决 · 严重级别：SEV-2 · 影响时长：11 分钟 · 作者：值班工程师

## 摘要（TL;DR）

一次配置变更将 `/api/items` 的故障注入开关 `FAILURE_RATE` 误设为 `0.3`，导致约 30% 请求返回 503，Grafana 错误率面板冲破 5% 阈值触发 `HighErrorRate` 告警。通过指标锁定 endpoint、日志确认注入标识、回滚配置恢复。无数据丢失。

## 影响

- 受影响服务：`showcase-api`（dev 环境）
- 用户影响：约 30% 的 `/api/items` 请求返回 503，持续约 11 分钟
- 数据影响：无（该接口只读）

## 时间线（UTC+8）

| 时间 | 事件 |
|------|------|
| 14:02 | 变更：通过 CD 流水线将 dev 环境 `FAILURE_RATE` 从 `0` 改为 `0.3`（用于故障演练，未及时还原） |
| 14:04 | Prometheus `HighErrorRate` 告警 firing，值班收到通知 |
| 14:05 | 打开 Golden Signals 面板，确认 5xx 集中在 `/api/items`，QPS 无明显下降 → 排除流量激增 |
| 14:06 | `kubectl logs -l app=showcase-api` 发现大量 `detail=injected upstream failure` |
| 14:07 | 检查 Deployment env，定位到 `FAILURE_RATE=0.3` |
| 14:09 | 执行 `kubectl set env deployment/showcase-api FAILURE_RATE=0`，触发滚动更新 |
| 14:13 | 错误率回落至 0，告警 resolve，冒烟测试通过 |
| 14:15 | 事件关闭 |

## 根因（5 Why）

1. 为什么返回 503？→ 故障注入开关被打开。
2. 为什么开关被打开？→ 演练时手动修改了环境变量。
3. 为什么没有还原？→ 演练流程缺少「恢复检查清单」和自动过期机制。
4. 为什么配置变更没有二次确认？→ dev 环境允许直接改 env，无审批。
5. **根本原因**：故障注入能力缺少「带 TTL 的开关」与「演练后强制还原」的流程约束，属于流程缺失而非代码缺陷。

## 处理与恢复

- 立即：将 `FAILURE_RATE` 复位为 `0`，滚动更新。
- 验证：`curl /healthz` 正常，错误率归零，告警 resolve。

## 经验教训（What went well / bad）

**做得好的**
- 监控先于用户反馈发现问题（告警 2 分钟内触发）
- Golden Signals 面板让定位 endpoint 只用了 1 分钟
- 回滚操作简单、可预测

**做得不好的**
- 演练变更未走审批，也未登记
- 故障注入开关没有自动过期
- 告警通知未联动演练窗口，造成误判风险

## 改进项（Action Items）

| # | 行动 | 优先级 | 状态 |
|---|------|--------|------|
| 1 | 故障注入改为带 TTL 的开关（如 `FAILURE_TTL_SECONDS`），到点自动失效 | P0 | 已完成 |
| 2 | 演练走独立 `chaos` namespace，禁止直接改生产/dev 的 env | P1 | 进行中 |
| 3 | Runbook 增加「演练后还原检查清单」 | P1 | 已完成 |
| 4 | 告警接入维护窗口静默，避免演练误报 | P2 | 计划中 |
